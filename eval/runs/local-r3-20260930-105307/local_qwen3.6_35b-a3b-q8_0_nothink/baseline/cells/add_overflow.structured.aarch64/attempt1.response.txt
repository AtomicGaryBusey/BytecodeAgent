Wait, the above logic for overflow is slightly flawed in assembly representation. Let's re-evaluate signed overflow detection.
Signed overflow occurs if:
1. `a > 0` and `b > 0` and `sum < 0` (positive + positive = negative)
2. `a < 0` and `b < 0` and `sum >= 0` (negative + negative = non-negative)

Alternatively, using flags:
Overflow flag V is set if the carry into the sign bit differs from the carry out of the sign bit.
ARM's `ADD` sets N, Z, C, V.
We can check V directly? No, we don't have an easy way to branch on V only without conditional moves or checking N and C.
Actually, simpler logic:
If `a` and `b` have different signs, no overflow is possible.
If `a` and `b` have same sign:
- If both positive (`x0 >= 0`, `x1 >= 0`) and result is negative (`x0 < 0`), overflow.
- If both negative (`x0 < 0`, `x1 < 0`) and result is non-negative (`x0 >= 0`), overflow.

Let's use X9, X10 as scratch.
1. Add `x0 = a + b`. Flags set.
2. Check sign of original `a` (need to save it or re-evaluate? We lost `a` in `x0`).
We must save `a` and `b` before adding if we want to check their signs easily, OR use the flag properties.

Correct Logic for Signed Overflow with Flags:
Overflow V = 1 if:
- Add two positives and get negative.
- Add two negatives and get non-negative.

Let's preserve inputs in callee-saved or stack? No, just use flags carefully or save inputs.
Since `a` and `b` are in x0, x1.
Let's move `a` to x19, `b` to x20 (callee saved).
Then add x19 + x20 -> x0.
Now we have original signs in x19, x20.

Refined Plan:
1. Move x0 (a) to x19.
2. Move x1 (b) to x20.
3. Add x19, x20 into x0 (sum).
4. Check if x19 >= 0 and x20 >= 0. If so, check if x0 < 0. If x0 < 0, overflow = 1.
5. Check if x19 < 0 and x20 < 0. If so, check if x0 >= 0. If x0 >= 0, overflow = 1.
6. Otherwise overflow = 0.

This is clean.
